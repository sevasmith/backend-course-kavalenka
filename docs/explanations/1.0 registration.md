# Backend Registration & Security Reference Guide

---

## 1. Registration Flow & Server-Side Guarantees

### Why the Server Enforces Email Confirmation
* **The Rule:** The decision to require email verification—and which method to use (6-digit OTP code or Magic Link)—must be strictly determined by **server-side configuration**, never by a parameter from the client.
* **The Threat:** If a client could include a flag like `{"skipEmailConfirmation": true}` in the registration request, an attacker could register any email address they do not own and instantly gain full access without verifying ownership.

### Taking the Email Before Activation
* **The Rule:** As soon as a user registers, their email is immediately treated as **taken** in the database (with status `pending`).
* **The Mechanism:** Any subsequent registration request using that same email must be rejected with an immediate conflict error (HTTP `409 Conflict`).
* **Storage Flexibility:** Developers may change internal database structures (e.g., separate staging tables vs. a single `users` table), provided the external API behavior remains identical: an unactivated `pending` account reserves the email address and prevents duplicate signups.

## 2. Password Hashing vs. Challenge Hashing (Two Separate Worlds)

A common point of confusion is treating passwords and verification codes with the same logic. They solve completely different problems and use entirely different technologies:

| Feature | Passwords (Long-term) | Confirmation Codes / Links (Short-lived) |
| :--- | :--- | :--- |
| **Algorithm** | **Argon2id** (preferred) or **bcrypt** (\\(\text{cost} \ge 12\\)) | **HMAC-SHA256** |
| **Speed** | Deliberately **slow & resource-intensive** (costs CPU & memory to prevent offline cracking) | Very **fast & lightweight** |
| **Secret Key** | **None.** bcrypt/Argon2id do not use a server configuration key. | Requires a dedicated **HMAC key** (\\(\ge 32\\) bytes) from server config. |
| **Salt** | **Unique random salt generated per user** and embedded directly in the hash string. | Uses the server's global HMAC key. |

### Why "The HMAC key does not replace the password salt"
* **The HMAC Key is Global:** One secret key in server configuration serves all users.
* **The Password Salt is Unique:** Every single user gets a unique, randomly generated salt.
* **The Danger:** If a developer skipped per-user salts and only hashed passwords with the server’s HMAC key, two users with the password `Secret123!` would have **identical hashes** in the database. If one account was compromised, all identical accounts across the system would be exposed.

## 3. Email Challenges: OTP Codes vs. Magic Links

The backend stores verification secrets in the database as **HMAC-SHA256** hashes:
\\[\text{Secret} + \text{HMAC Key} \longrightarrow \text{64-character hash (256 bits)}\\]

The plaintext secret is sent to the user's email and **never** stored in the database.

### The 6-Digit OTP Vulnerability (Why We Need `attemptId`)
1. **The Math:** A 6-digit number has only **1,000,000 possible values** (`000000` to `999999`).
2. **The "Whole Table" Attack:** 
   * An attacker does not need the server's secret key. 
   * If the API allowed verifying with just a code (`POST /confirm` with `{"code": "123456"}`), the attacker would simply make the server compute the HMAC and check if *any* pending user matched. 
   * With thousands of users awaiting confirmation, testing a few thousand numbers would hijack random accounts within seconds.
3. **The Solution (The Identifier):**
   * The server forces the client to supply an **`attemptId`** (the specific attempt record / "locker").
   * The server checks **only that one record**.
   * The server strictly enforces a limit of **5 failed attempts** before permanently invalidating (`consuming`) the attempt.

### Magic Links Do Not Need an `attemptId`
* Magic links use a **32-byte cryptographically secure random token** (approx. \\(10^{77}\\) combinations).
* Because the space of possible tokens is astronomically vast, guessing a valid token is mathematically impossible. The server can look up the attempt directly by computing the HMAC of the incoming token.

## 4. How the Frontend Handles the `attemptId`

Users never type or see the `attemptId`. The browser frontend handles it programmatically:

1. **User clicks "Register":**  
   Browser sends `POST /auth/register` with credentials.
2. **Server responds:**  
   Returns HTTP `202 Accepted` with JSON:
   ```json
   {
     "confirmationRequired": true,
     "method": "otp",
     "attemptId": "c4a1b234-89ab-4cde-...",
     "expiresInSeconds": 600
   }
   ```
3. **Frontend stores it:**  
   JavaScript keeps `attemptId` in component memory (state) or temporary page storage.
4. **User enters 6 digits:**  
   When the user submits the form, JavaScript silently bundles both values together:
   ```json
   {
     "attemptId": "c4a1b234-89ab-4cde-...",
     "code": "482910"
   }
   ```
   and sends them to `POST /auth/register/confirm`.

## 5. Defense Against Specific Attacks

### Constant-Time Comparison (Preventing Timing Attacks)
* **The Vulnerability:** Standard string equality checks (`===`) check character-by-character and stop immediately on the first mismatch. Checking a guess with 5 matching characters takes slightly longer than one with 0 matches. Attackers can measure network latency down to nanoseconds to guess secrets character by character.
* **The Fix:** Constant-time comparison functions (like `crypto.timingSafeEqual` in Node.js or `hmac.compare_digest` in Python) always inspect every single byte regardless of mismatches, ensuring identical execution time for every request.

### Activating Magic Links with `POST`, Not `GET`
* **The Vulnerability:** Antivirus software, spam filters, and email clients (like Outlook or Gmail) automatically pre-fetch links in incoming emails using HTTP **`GET`** requests to scan for malware.
* **The Problem:** If opening the link (a `GET` request) activated the account, the security scanner would consume the single-use token before the human ever saw the email. When the user clicked the link later, they would receive an error that the token had already expired or been used.
* **The Fix:** The link opens a webpage (safe `GET`). The actual activation occurs only when the human clicks an **"Activate Account"** button, triggering an intentional **`POST /auth/register/confirm`** request.

## 6. Cryptographic Key Isolation

The backend mandates strict key separation. Secret keys must be at least **32 bytes (256 bits)** long and cannot be shared across different subsystems:
* **`JWT_ACCESS_SECRET`**: Strictly signs 15-minute access tokens.
* **`JWT_REFRESH_SECRET`**: Strictly signs 30-day refresh tokens.
* **`LOGIN_CHALLENGE_HMAC_KEY`**: Hashes login and registration OTP challenge secrets.
* **`EMAIL_CHANGE_HMAC_KEY`**: Hashes email modification challenge secrets.
* **`DELETION_CHALLENGE_HMAC_KEY`**: Hashes self-deletion challenge secrets.
