## Notes

- **Table name:** `task.md` and the theory call the table `grants`, not `role_permissions`.
- **Bootstrap scope:** `task.md` adds the `transformations` permission and gives the `user` role only to *active* users without roles. The theory file leaves out `transformations` and says "every existing user". Follow `task.md`.
- **Bootstrap admin on a fresh DB (our choice, confirm with the mentor):** a fresh DB has no users, so the variable is optional and the bootstrap is skipped until the user exists. Running it without an admin would make RBAC non-empty, so it would never run again and nobody could get `rbac@manage`. To get the first admin: register a user, set its id in `RBAC_BOOTSTRAP_ADMIN_USER_ID`, and restart. This matches `task.md`, where registration assigns `user` only "if the RBAC module is initialized".
- **Routes without a decorator (our choice, confirm with the mentor):** `task.md` allows blocking them at startup *or* returning 503. We block at startup, so the mistake shows up in dev or CI and not in production.
- **Deleting roles and permissions in use:** `grants` cascades on role/permission delete in the DB, but the API must return 409 for one that is in use. The service checks for use first, so the cascade never fires through the API.
