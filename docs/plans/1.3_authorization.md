# 1.3 Authorization — Plan

## Overview

1. **Look at the chain we already have** (task 1)
   The access check, the CSRF check and RBAC already exist from 1.1 and 1.2. First we check each step of 1.3 against the code, so we only build what is missing.

2. **Fix the error answers** (task 2)
   When the users database is down, the guard must say `authorization_unavailable`. No error may show the user's roles, status or the needed permission.

3. **Add a third kind of route: the receipt** (tasks 3–5)
   Some routes can be opened by a special header instead of a login. Deleting an account needs this later in 1.6. We teach the decorators, the guards and the startup check about it.

4. **Check who owns the thing** (task 6)
   Some actions are allowed only on your own data, unless you have an `*_any` right. We make one shared helper for this, so the next parts (1.4 and later) can use it.

5. **Write down every refusal in the logs** (tasks 7–8)
   Each 401, 403 and 503 gets a fixed reason in the log, and each RBAC decision records who asked for what. Secrets never go into the logs.

6. **Describe it and test it** (tasks 9–12)
   OpenAPI shows which routes need the cookie. Tests prove the order of the checks and every way a request can be refused. Then we run lint, tests and build.

**In the end:** every route is public, protected by one `permission@action` pair, or opened by a receipt; every protected request goes through access → user status → CSRF → RBAC → ownership in this order, and answers the right 401, 403 or 503.

## Notes

- **503 code when the users DB is down:** 1.3 says `authorization_unavailable`; `task.md` lists both `authorization_unavailable` and `service_unavailable` for 503. The 1.2 guard uses `service_unavailable`. Follow 1.3 for the guard (task 2); the auth endpoints (refresh, login) keep `service_unavailable`.
- **Undeclared routes:** 1.3 says they drop readiness; `task.md` allows blocking at startup *or* 503. In 1.1 we chose to stop the app at startup. Keep that choice (already noted for the mentor in the 1.1 plan).
- **Order of `*_any`, lookup and 404:** the theory says the `*_any` check comes after the base right and *before* looking up the target; §1.3.4 says load the resource, then 404, then ownership. For users the owner is the id itself, so no lookup is needed. For transformations (2.x) ask the mentor which order to use.
- **Receipt route without the header and without a pair:** 1.3 says "a pair is required" but not which status to return. Ask the mentor; until then, deny (401, since no identity is established).
- **Client refresh (§1.3.3):** single-flight refresh and one retry are client work, and this repo has no frontend. Ask the mentor whether anything is expected here (for example a short doc or a sample client).
- **"Critical operations" in the audit:** 1.3 asks to log successful admission to them but doesn't list them. Suggested: `rbac@manage`, every `*_any` and every `delete`. Confirm with the mentor.
- **Readiness only for internal infrastructure:** 1.3 says it *may* be; nothing to build unless the mentor asks.
- **No protected business endpoints yet:** only `/admin/rbac/*` exists. E2e tests can use those plus a small test-only controller in the test app.
