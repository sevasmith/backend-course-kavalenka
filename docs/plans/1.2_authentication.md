# 1.2 Authentication — Plan

## Overview

1. **Add the secret keys and settings** (tasks 1–2)
   Login needs secret keys to sign tokens and settings to turn the email step on or off. The app must refuse to start if a key is missing or too short, so we do this first.

2. **Make a table for login attempts** (task 3)
   When login asks for an email code, we must remember the attempt somewhere. This table is the only new table for this part.

3. **Learn to make and check tokens and cookies** (tasks 4–5)
   We build small helpers that create the two tokens, check them, and put them into cookies or clear them. Login, refresh and logout all use these helpers.

4. **Let people log in with email and password** (tasks 6–8)
   A user sends email and password and gets two cookies. Wrong data always gets the same answer, so nobody can learn which emails exist. We also limit how often someone can try.

5. **Add the email step for login** (tasks 9–12)
   When the setting is on, the user first gets a code or a link by email and must confirm it. They can ask for a new one after 60 seconds.

6. **Let people stay logged in and log out** (tasks 13–14)
   Refresh gives a new pair of cookies without the password. Logout always clears the cookies.

7. **Check the token on every protected request** (tasks 15–16)
   Every protected endpoint first checks the access cookie and that the user is still `active`. Then RBAC gets the real `userId` instead of the stub. Requests from other sites must pass the CSRF check.

8. **Clean up and check everything** (tasks 17–21)
   Return the right errors, write safe logs, describe the endpoints in OpenAPI, write tests, and run lint, tests and build.

**In the end:** a user can log in (directly or with an email code or link), stay logged in with refresh, log out, and every protected endpoint knows who is calling.

## Notes

- **Overlap with 1.3 Authorization:** the access check (1.2 §1.3.6) and the CSRF check are described in both files. Here we build the guard that sets `userId` and the CSRF check; 1.3 then confirms the full chain order (access → status → CSRF → RBAC → ownership).
- **Login challenge lookup differs from registration:** 1.2 finds a magic link attempt by `attemptId` from the token `attemptId.secret`, while the registration code finds it by the token's HMAC. Follow 1.2 for login; don't copy the registration lookup.
- **No `expires_at` in `login_challenges`:** 1.2 computes it as `last_sent_at + 10 min` (BCNF), unlike `registration_challenges`, which stores it. Seva's ER diagram already matches.
- **Separate HMAC keys:** `task.md` only names `LOGIN_CHALLENGE_HMAC_KEY`. The project already has `REGISTRATION_CHALLENGE_HMAC_KEY`; keep them separate, since 1.2 forbids sharing a key.
- **Open question — rate limit storage:** the current throttler counts in process memory, so with several instances each has its own counter. `task.md` makes PostgreSQL the only source of truth. Ask the mentor whether in-memory limits are acceptable or the "5 failures per email + IP" counter should live in the DB.
- **Open question — key for logging unknown emails:** 1.2 asks for "an irreversible internal identifier with a separate key", but no env variable is named. Ask the mentor; until then, add a separate key (e.g. `AUDIT_LOG_HMAC_KEY`) with the same ≥ 32-byte rule.
- **Open question — `Secure` cookies in local development:** 1.2 forbids any exception for HTTP. Browsers accept `Secure` cookies on `localhost`, but some HTTP clients don't send them over plain HTTP. Ask the mentor whether local testing should use HTTPS.
- **Magic link page URL:** the docs say the link opens a page and passes the token in the URL fragment, but don't name the variable. Reuse the registration pattern (`REGISTRATION_CONFIRM_URL`) with a login equivalent.
